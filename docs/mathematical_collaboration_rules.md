# 数学共同研究のルール

作成日：2026年9月14日  
対象：Takuya Abe とAIアシスタントによる数学・数理物理の共同研究  
版：1.0

## 1. 目的と適用範囲

直感的な対話から、先行研究の確認、証明構築、Lean検証、論文化までをつなぎ、後になって既知の結果との重複や仮定の不足が判明する手戻りを減らす。

本書を共同研究の既定手順とする。案件ごとの明示的な指示を優先する。通常の概念解説・翻訳・校正だけの依頼には、文献調査やLean形式化を一律に要求しない。

基本方針は、**直感を自由に探索し、問いが定まったら既知との差を確認し、固まった補題から検証する**ことである。全ての思いつきを直ちに形式化する必要はない。

## 2. 研究の標準的な流れ

| 段階 | 実施する作業 | 残すもの |
| --- | --- | --- |
| 直感の探索 | 動機、具体例、期待する現象を対話する | 問いの候補と例 |
| 定式化 | 対象、仮定、量化、結論を明示する | 正確な目標と部分的な目標 |
| 初期文献調査 | 最も近い既知の定理と適用条件を調べる | 既知との比較と未確認事項 |
| 証明・反例探索 | 成否を左右する核心を優先して試す | 証明、反例、具体的な障害 |
| 随時Lean検証 | 安定した定義と独立して使える補題を検証する | 宣言、実行記録、原稿との対応 |
| 文献の再照合 | 結果・手法・定式化の変化に応じて調べ直す | 更新された貢献候補 |
| 論文化 | 証明、引用、位置づけを統合する | 根拠と主張が一致した原稿 |

これは固定的な一方向の工程ではない。反例や文献によって必要な段階へ戻る。重要な変更がない限り、同じ調査と監査を繰り返さない。

## 3. 先行研究を調べる規則

### 調査の時期

大きな証明や多数の周辺結果に着手する前に、最も近い既知の結果を確認する。直感の探索を長く続ける場合も、問いが検索可能な形に定まったところで一度照合する。

次の場合は再検索する。

- 主定理の仮定や結論が変わった。
- 別分野の構成や理論との対応が見つかった。
- 証明手法が明確になった。
- 主定理が完成した、または投稿用の新規性を主張する段階になった。

### 調査の深さ

関連論文の一覧や要旨の類似だけで調査完了としない。最も近い一次文献の正確な版と定理を読み、対象・仮定・結論を比較する。直接適用、記号の翻訳、短い系で今回の結果が得られないか確認する。

独自の名称だけで検索せず、対象の名前、同値な表現、同義語、古い用語、隣接分野の用語を使う。参考文献と利用可能な前方引用もたどる。重要な新規性候補は別の検索方針でも確認する。

出典、版、定理番号、確認日、適用条件、検索語と検索範囲、未確認部分を記録する。未公開原稿全体を検索サービスへ送ることを既定にせず、必要な概念や抽象化した語句を使う。

### 調査結果の扱い

「既知」「記号の翻訳で一致」「既知の結果の系」「既知の別証明」「部分的な重複」「調査範囲内で新規の候補」「確認した文献で未解決とされる」を区別する。未確認は未確認と記す。

検索で見つからないことを未発表の証明としない。原文が入手できなければ、その適用や新規性の判断を保留する。依存しない探索は進められる。

重複が判明したら貢献の説明を訂正する。仮定の緩和、結論の強化、構成的手法、別証明、応用などの差分を調べ、差分が残らなければその路線での新規性追求を止める。名称の変更で新規性を維持しない。

## 4. 証明を作る規則

研究全体を左右する、まだ確かでない一歩を常に特定する。その証明・反例・文献確認を、周辺の計算や文章の整備より優先する。

各補題について使う仮定と得られる結論を明示する。境界例、退化例、低次元例、仮定を外した例は、具体的な疑義を解消するために使う。有限計算や数値実験を一般定理へ昇格させない。

失敗した証明方法、命題への反例、実装の不具合、文献へのアクセス障害を区別する。原稿の主張が誤っている場合は、追加仮定の下で成立する修正版と元の主張を分ける。原本や目標を無断で書き換えない。

AIの活用は、補題への分解、仮定の追跡、具体例と反例候補、定式化の翻訳、検証に重点を置く。能力の自己評価や説明の流暢さを根拠としない。扱いやすいからという理由で、元の幾何・代数の問いを不等式の問題へすり替えない。

## 5. Leanを組み込む規則

### 形式化する単位

基本定義が安定し、他の議論から独立して使える補題が完成したら形式化する。特に、後続の依存が多い補題、商や写像の定義の適切性、例外条件に関わる主張を優先する。

定義を頻繁に変更する探索段階では、Lean実装を保留できる。その場合も形式化予定と未検証範囲を残す。環境の構築が難しい場合は数学の議論を継続し、実行していないコードを検証済みと扱わない。

### 検証の内容

固定したLean・依存ライブラリの環境で実際にビルドする。原稿の対象・仮定・量化と宣言の型を照合する。抽象モデルで証明した場合は原稿の対象との橋渡しも証明する。

型クラスや構造体のフィールドで結論を仮定していないか確認する。Leanの実装エラーを即座に数学的な誤りと扱わず、型や表現、ライブラリ、実行環境、証明の問題を切り分ける。

完了成果には証明穴や独自の未証明公理、検証を迂回する仕組みを残さない。必要な宣言について推移的な公理依存を監査し、標準論理公理への依存は記録する。

ビルド成功だけでは原稿全体の形式化完了にならない。付録・具体例を含む依頼範囲の意味上の対応を最終的に点検する。Lean検証は新規性の証明でもない。

## 6. 状態を混同しない

各主張に安定した識別子を付け、以下を別々に記録する。

| 観点 | 記録する状態の例 |
| --- | --- |
| 数学 | 証明案、未解決の含意、確認済み、反例あり |
| 文献 | 未調査、既知、既知の系、別証明、新規の候補 |
| Lean | 未着手、部分検証、実行失敗、検証済み |
| 意味上の対応 | 未確認、部分対応、原稿との対応確認済み |
| 論文上の役割 | 背景、道具、主結果候補、応用、限界 |

正しさ、新規性、説明・再利用上の価値、投稿先との適合性は別の根拠で評価する。証明が難しかったことや形式化の量を新規性の根拠にしない。

## 7. 記録、変更、再開

小さな案件は一つの研究ノートでよい。大きな案件では既存の台帳やプロジェクト構成を使い、次の内容を保持する。

- 問いと貢献候補。
- 正確な主張、定義、仮定、依存関係。
- 文献の比較と確認範囲。
- 証明、Lean宣言と検証記録、失敗の理由、次の一手。

定義・仮定・引用の解釈が変わったら、依存する証明、Lean宣言、文献比較、原稿を特定し、再確認待ちにする。撤回・訂正の理由を残す。影響のない検証を根拠なくやり直さない。

長い作業は原稿とソースの版またはハッシュ、最後に成功した検証、未解決箇所を保存する。「続けて」と依頼されたら、実ファイルと記録を照合して作業を再開する。記録の量を研究の進展とみなさない。

## 8. 論文化と完了判定

研究中から、主張・証明・関連研究・差分・限界を原稿の骨格に統合する。新規性を強く宣言する序論は、文献との比較が固まってから仕上げる。

論文をまとめる際は、次を確認する。

- 主張の仮定と証明が一致し、核心の未解決箇所を隠していない。
- 外部定理の出典と適用条件が確認されている。
- 既知との関係と貢献の説明が調査の根拠に合っている。
- 依頼されたLean形式化の範囲、実行結果、意味上の対応が明示されている。
- 配布する原稿・コードが検証した版と一致している。

「数学的証明が完成」「Lean形式化が完成」「投稿用原稿が完成」を区別する。全体完了は依頼範囲全体が確認された場合だけに使う。未解決問題の解決、新規性、採録を保証しない。

## 9. 対話と進捗報告

説明では動機と直観から入り、記号を初出時に定義し、定義・具体例・式・概念間のつながりを段階的に示す。共有済みの事項を毎回長く説明し直さない。

進捗は原則として「今回確定したこと／既知との関係／残る核心／次に確認すること」を簡潔に伝える。既に許可された通常の研究作業を、不要な確認のために止めない。目標の実質的な変更が必要な場合は理由と選択肢を示す。

## 10. 次回の使い方

新しい研究では、原稿や問いとともに「この共同研究ルールに従って進めてください」と指定する。個人スキルを使える環境では `$mathematical-dialogue` を指定し、補題の形式化には `$lean-formalization` を使う。

この文書を保存するだけで、全ての環境・会話へ自動適用されるわけではない。別環境では本書を添付するか、プロジェクトの指示から参照する。今回の設定では、既存の「数学の対話と研究」スキルにも運用手順を反映する。
